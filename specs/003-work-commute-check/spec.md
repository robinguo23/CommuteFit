# Feature Specification: Work Commute Check / 求职通勤检查

**Created**: 2026-10-28  
**Status**: Iteration in progress  
**Input**: 求职者填写每周可上班时间和单程通勤上限，输入招聘 URL、职位描述或工作地点，判断职位班次与去返程通勤是否适合。

## User Scenarios & Testing

### User Story 1 — 评估工作班次和往返通勤 (P1)
用户只需填写出发 postcode/常用地点、单程通勤上限、每周可上班的星期和时段，以及工作信息。工作信息可以来自招聘 URL、粘贴的职位描述或直接输入工作地点 postcode。用户确认或修改职位地点、工作星期和上下班时间后，系统查询去程和回程并给出合适、待确认或不太合适的判断。

**Independent Test**: 提交完整的一周工作安排和可解析地点；验证去程使用 Arrive at shift start、回程使用 Leave at shift end；比较两程各自最短的可用路线与单程上限，并检查职位的每个工作日和整个班次是否落入用户可用时间。

**Acceptance Scenarios**:
1. 完整信息、两程均有上限内路线、班次符合每周可上班时间时，显示“通勤合适”。
2. 任一方向已确认的可用路线均超过上限时指出具体原因；班次与用户时间冲突时提示确认能否调整。
3. 必要信息缺失、路线时长不足、TfL 没有返回路线或服务失败时，显示“可能合适／待确认”或明确服务错误；未知不得当作不合适。
4. 显示每个已查询工作日的去返程路线、预计时长、换乘数和交通段。
5. 用户输入 URL 或职位描述后，系统尽可能提取 postcode、星期和明确的 12 小时制班次；提取值进入可编辑字段并明确作为建议待确认。
6. URL 无法读取、出现多个 postcode 或信息不清时保留手动补充路径；不能静默选一个似乎相关的地点。
7. 用户直接输入工作 postcode 后可以手动填写全部职位星期和班次信息。
8. 模糊地点可通过 TfL 地点候选选择；无法解析时保留候选/错误说明，允许修改位置。
9. 工作通勤结果不展示、不推断、不使用票价。此流程不调用 FareTo。

## Requirements

### Functional Requirements
- **FR-001**: 收集出发地点、1 至 1440 分钟单程时长上限；每周可上班星期和时间范围为选填。
- **FR-002**: 工作信息来源三选一：URL、粘贴职位描述、工作地点 postcode；所有来源最终汇入可编辑的工作地点、工作星期、上班和下班时间字段。
- **FR-003**: 提取结果只是候选值，用户可以修改。无法读取网页、无法确定必要信息、多个邮编候选时说明原因并请求补充。
- **FR-004**: 去程调用现有 Journey Planner 能力，以出发地点到工作地点并按上班时间 Arrive 查询。
- **FR-005**: 回程以工作地点到出发地点并按下班时间 Leave 查询；过夜班次的下班时刻使用次日日期。
- **FR-006**: 比较每个工作日两个方向的路线时长与单程上限。某方向至少一个有时长的路线在上限内即可确认该方向可行；所有有时长路线均超限但还存在时长缺失路线时，该方向待确认。
- **FR-007**: 对比完整工作班次和用户填写的可上班时间。时间冲突须明确说明并提示确认调整；只有用户明确表明不可调整时才可视为硬性不符合。未填写不能视作全天可用。
- **FR-008**: 仅所有必要信息完整、排班兼容、每个已列工作日去返程均有上限内路线时，判为“通勤合适”。明确时长超限判为“不太合适”；可调整性未知的排班冲突判为“可能合适／待确认”。
- **FR-009**: 展示去程、回程每条 TfL 路线的预计时间、换乘次数和各交通段；分别呈现不适合原因、待确认原因或服务不可用。
- **FR-010**: 这个工作通勤 API 的响应不包含票价字段；不调用 FareTo，不以票价参与任何判断。原 `/api/journeys` 单独路线页面的既有能力不属于本功能的评估逻辑。
- **FR-011**: 地点搜索和 Journey Planner 延用既有服务端候选 token，往返查询时随地点交换对应 token。
- **FR-012**: URL 抓取只接受 HTTP(S) 公网主机、不跟随重定向，限制等待时间和响应体大小；网页抓取失败时允许粘贴文本或手动填写。
- **FR-013**: 当岗位班次未知时，显示未来连续七个伦敦当地日期的横向卡片，每天四个参考班次；默认先展示通勤结论，点击展开路线和换乘详情。
- **FR-014**: 支持通用、超市、咖啡店、餐厅参考组合，时间可编辑；行业可选，示例组合及时间见 shift-template-proposal.md。切换模板前保护用户已修改的时间。
- **FR-015**: 具体岗位时间优先用于实际班次查询。参考班次仅判断该具体时间点的通勤，并明确实际岗位班次待确认；不得推断岗位提供该班次。
- **FR-016**: 用户可选择查看任意参考场景；查询失败、无路线或时长未知保持待确认，各方向独立显示；修改地点、上限、时间后旧结果不可误认为新结果。
- **FR-017**: 班次可以跨午夜，按实际次日查询返程；卡片展示具体日期与次日下班标识。默认缓冲为零，不自动增加到岗或离店时间。
- **FR-018**: 多个岗位班次可能为选项或轮换，未确认前不得因一个班次冲突推断整个岗位不合适。

### Non-Goals
- 不收集票价预算，不使用 FareTo，不按交通段叠加票价。
- 不做账号、个人档案、保存职位、职位申请资格判断、交通方式偏好或招聘网站专用集成。
- 不承诺读取需登录、强反爬、脚本渲染或有访问限制的招聘页面。
- 首版不推断普通街道地址、雇主名称或复杂轮班模式。

## API Contract

- `POST /api/work-commute/extract`: `{ sourceType: "url" | "description" | "work-postcode", content }` → 可为空的 postcode、工作星期、班次时刻和解释 notes。
- `POST /api/work-commute/assess`: 输入出发地点、单程上限、用户可用星期/时段、工作地点、工作星期、班次时刻及可选地点 token → `status`, `scheduleStatus`, 各工作日 `outbound` 和 `returning` 路线。
- 工作通勤 `Route` DTO 只暴露路线时间、duration、transfers 和 legs，不包含 fare。
- 现有 `POST /api/journeys` 保持为独立路线查询底层/页面能力。

## Key Entities

- **Weekly availability**: 用户可上班星期，以及当日最早可开始/最晚结束的本地时间范围。
- **Job schedule**: 工作星期、上班时间和下班时间；若结束时间早于开始时间，则视为次日结束。
- **Direction assessment**: 目标时刻、Planner 路线列表、最佳已知时长、上限状态和说明。
- **Work commute result**: 总状态、班次兼容状态、逐工作日去返程结果和原因；无价格。

## Success Criteria

- 去程和回程分别采用正确的 Planner 时间语义和反向地点候选 token。
- 无路线、未知时长或服务不可用不会产生“不太合适”的误判。
- 自动提取失败时，用户可以手动补全并继续完成评估。
- 自动化测试覆盖匹配/冲突/超时/缺路线/过夜班次/职位文本提取歧义等核心分支。

## Extraction Limitations

- 当前只用轻量规则提取：英国 postcode、常见英文星期及 Monday–Friday/weekends、明确的 `9am–5:30pm` 一类时间范围。
- 有多个 postcode 时不猜哪个是工作地点；普通地址、轮班文字、不同日期不同班次、时区和日期例外需要用户确认或手动填写。
- 网页内容仅抓取静态可访问 HTML；登录页、JavaScript 渲染、验证码、robots/反爬拦截、站点条款和网络策略都可能导致读取失败。
- 抽取不等于招聘网站官方数据，用户应核对被预填的字段。
