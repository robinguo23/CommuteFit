# Feature Specification: 简化通勤初筛与按需时间搜索

**Feature Branch**: 未创建；当前工作区没有 Git 仓库。

**Created**: 2026-10-29

**Status**: Implemented and packaged — 自动化及首页界面检查通过；新后端的真实路线页面验收待本地重启。具体结果及边界见CHANGELOG。

**Input**: 用户要求按小区域 postcode 做投递前初筛；时间可选，默认从今天起查七天；页面只保留主要结论。参考时间逐点尝试，找到符合上限的路线即停止，复用重复日期和时间点。

## User Scenarios & Testing

### User Story 1 - 用简单输入获得投递参考 (Priority: P1)

求职者给出出发地、岗位所在小区域和单程通勤上限，无需准确门店地图确认或必填 availability，即可得到一个主要结论及简短原因。

**Why this priority**: 先判断岗位是否值得继续了解，降低找门店和填写排班的负担。

**Independent Test**: 输入两个完整 postcode 并保留默认时间条件，得到一个主要结果；详细日期、路线和换乘默认折叠。

**Acceptance Scenarios**:

1. **Given** 没有岗位班次和个人时间，**When** 开始初筛，**Then** 使用伦敦今天及之后六天的参考时段，并标注结果是按参考时段判断。
2. **Given** 岗位有明确班次，**When** 初筛，**Then** 按岗位时间查询到岗去程及下班回程，不用默认时段替换。
3. **Given** 用户只提供可工作窗口，**When** 初筛，**Then** 窗口限制参考选择，不把整个窗口伪装成一条实际班次。
4. **Given** 用户只知道小区域 postcode，**When** 初筛，**Then** 无需选择准确门店或地图点；说明结果是区域级判断。
5. **Given** 没有明确班次且用户只选择日间参考，**When** 初筛，**Then** 只查七天日间去回，不额外查询早班、晚班或第八天上午节点。
6. **Given** 用户同时选择日间与早班，**When** 日间已命中，**Then** 仍完成所选早班检查，不由系统自动跳过；每个方向内部仍按候选顺序命中即停。
7. **Given** 用户选择的日间往返可行、早班去程不符合，**When** 汇总，**Then** 显示“可以通勤，可以尝试投递”，注明“日间往返符合要求，早班去程不适合”，不以早班失败否定日间机会。
8. **Given** 部分日期的已选参考往返可行、其余日期不符合，**When** 汇总默认初筛，**Then** 保留正向结论并说明适用日期，不声称全周可行。

### User Story 2 - 按优先顺序试时间，命中后停止 (Priority: P1)

每个方向只寻找第一条符合条件的参考时间，并展示该时间下最优的合格路线；不会为了生成大批路线卡片把所有时间点都查完。

**Why this priority**: 减少等待和重复查询，同时保留明确的判断依据。

**Independent Test**: 设置某组第三个时间点命中，确认只查询前三个时间点，后续不查询；存在路线但超过上限不算命中。

**Acceptance Scenarios**:

1. **Given** 早班02:30已有符合上限的到岗路线，**When** 搜索早班去程，**Then** 不再查询03:30至06:30。
2. **Given** 晚班22:30未命中、21:30命中，**When** 搜索晚班去程，**Then** 不查询20:30。
3. **Given** 同一天早班已查询06:30，**When** 日间需要06:30，**Then** 复用该结果；成功则停止，确定失败才继续07:30。
4. **Given** 早班02:30命中且未查询06:30，**When** 查询日间，**Then** 仍需先查询日间06:30，不能把“早班已停止”当作06:30已经查过。

### User Story 3 - 共享回程并判断参考时段覆盖 (Priority: P2)

早班使用其日程当天上午的回程，晚班使用次日上午的回程。因此第二天早班可以复用第一天晚班已查到的第二天上午回程，减少一次重复检查；相同规则顺延。第一天早班无前一日晚班结果可复用时，独立查询第一天上午，不移到第二天。默认初筛检查时段交通覆盖，不构造假想班表，不设置最少工作时长。

| 七份日程中的参考 | 回程节点日期 | 复用关系 |
|---|---|---|
| 第一天早班 | 第一天上午 | 首日单独检查，不依赖不存在的第零天日程 |
| 第一天晚班 | 第二天上午 | 结果供第二天早班复用 |
| 第二天早班 | 第二天上午 | 复用第一天晚班，日期和方向相同 |
| 第六天晚班 | 第七天上午 | 结果供第七天早班复用 |
| 第七天晚班 | 第八天上午 | 仍归第七份日程，不新增第八份日程 |

**Why this priority**: 根据少量代表时间判断是否值得继续投递，减少重复查询与不必要的排班限制。

**Independent Test**: 周一晚班回程与周二上午回程的相同点只查一次；周一上午同一钟点仍是不同的查询。

**Acceptance Scenarios**:

1. **Given** 周一晚班已查询周二06:10回程，**When** 周二需要相同方向和时刻的回程，**Then** 复用结果，不重新查询。
2. **Given** 早班去程06:30命中，上午回程参考也已命中，**When** 进行默认初筛，**Then** 不施加四小时工时要求，不因两者不能组成四小时班表而标记待确认；该结果表示参考时段有交通，不显示成实际上下班安排。
3. **Given** 共享回程09:10没有合格路线而10:10命中，**When** 评估回程，**Then** 采用10:10结果并停止，不因09:10通常有交通而省略实际核对。
4. **Given** 服务不可用，**When** 无法判断某方向，**Then** 该方向保持待确认，不把请求失败当作没有交通。
5. **Given** 总共只有七份日程，第七天晚班去程已命中，**When** 查询该日程的回程，**Then** 使用落在第八天06:10至10:10的候选时间节点，命中即停，结果仍归第七份日程；不建立第八份日程，也不为第八天新增去程、日间或晚班参考。
6. **Given** 第一天上午已有回程结果，**When** 第七天晚班需要第八天上午的节点，**Then** 使用第八天的真实节点日期，不以第一天的同星期结果替换；日程数量仍为七份。
7. **Given** 正在检查第一天早班且无已有同日回程结果，**When** 生成回程检查，**Then** 独立查询第一天上午候选，不移到第二天，也不额外创建第零天日程寻找复用。
8. **Given** 第一天晚班已命中第二天07:10回程，**When** 检查第二天早班回程，**Then** 直接复用该第二天上午参考结果，不再重复查询该组上午回程；第一天早班仍使用第一天结果。

### Edge Cases

- 用户选择哪些参考类型就检查哪些；某一类型成功或失败均不自动跳过其他已选类型。未选类型不作为成功、失败或未知加入汇总。
- 今天已过去的时点若无法取得计划结果，标记未覆盖/待确认，不因该限制判不可通勤。
- 七天范围按班次开始日期计算：第七天晚班的回程落在第八天，照常检查，仍属于第七天晚班结果；第八天不额外开始一轮新班次检查。
- 同一日期/时刻在出发与到达两种要求下分别判断；起终点相反也分别判断。
- 一条候选路线有结果但超出上限，或到岗晚于目标时刻，不算可行。
- 只知道 postcode 的结果不保证准确门店或员工入口的最后一段步行。
- 部分日期可行、其他日期失败时，结论必须标注适用日期，不能宣称一周所有日期均可。
- 默认上午回程最多查到10:10，命中后不扩展后续时点。四小时只是用户选择参考时点的推理依据，不作为筛选、配对或待确认条件；明确岗位时间仍按实际时间查询。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 接受区域级完整 postcode，不强制准确门店、地图确认、账号或 availability；单程上限沿用现有可编辑默认60分钟。
- **FR-002**: 无明确班次时，系统 MUST 从伦敦今天起建立且仅建立连续七个日期的日程。当天晚班回程使用次日上午的时间节点；第七份日程的晚班回程使用第八天上午节点，结果归属第七份日程。节点日期可跨出七天范围，但日程数量不增加，不查询第八份完整日程，不额外新增第八天的去程、日间或晚班参考。
- **FR-003**: 明确岗位班次优先；没有岗位班次时，用户给出的明确时间用于其指定检查；双方都没有明确时间时才采用默认参考。个人可工作窗口用于约束和对比，不宣称等于岗位班次。
- **FR-004**: 默认早班去程的到岗目标 MUST 按02:30、03:30、04:30、05:30、06:30顺序逐点尝试，首个命中后停止。
- **FR-005**: 默认晚班去程的到岗目标 MUST 按22:30、21:30、20:30顺序逐点尝试，首个命中后停止。
- **FR-006**: 默认日间去程的到岗目标 MUST 按06:30、07:30顺序逐点尝试；回程只检查当日17:10出发。06:30如已查询则复用，但不得假定它一定已经被早班查询。
- **FR-007**: 早班/晚班共享上午回程候选06:10、07:10、08:10、09:10、10:10。对于日程日期D，早班回程使用D当天，晚班回程使用D+1次日；日间回程仍为D当天17:10。上午按顺序逐点尝试，首个符合单程上限的回程命中后停止，最多到10:10。D+1早班 MUST 复用D晚班已完成的同日历日期上午参考，避免再次检查；首日早班无同日结果时独立查首日上午。不设置最少工时，不按四小时配对。
- **FR-008**: 系统 MUST 复用同一出发地、目的地、具体日历日期、目标时刻和方向时间要求的相同查询；跨午夜只在实际日期一致时共享。不额外预查已经停止的分支。
- **FR-009**: 有路线且符合单程上限及目标时间才算命中。多条候选只取满足条件且耗时最短的一条，不直接将返回第一条视为最优。默认结果以方向时段覆盖作为初筛依据，不将参考时间拼成具体班表；有明确班次时按其实际到岗、离岗时刻分别查询。
- **FR-010**: 首屏 MUST 只给一个主要结论和必要原因，注明去程/回程以及适用的日期、参考时段。详细路线、日期卡片、来源和精确门店作为可展开附加内容；不按行业呈现默认模板。
- **FR-011**: 已确认不符合与无法判断 MUST 区分。只有已核对的检查范围全部确定不符合时，才能给该范围内“不可以通勤”；服务失败、地点不明、未覆盖时段保持“暂时无法判断”。不得将少量参考点失败扩大为整日或所有班次不可能。
- **FR-012**: 不设费用上限、不用票价参与判断、不使用 FareTo，不判断申请资格，不保证实时准点；不持久保存岗位、排班及路线结果。
- **FR-013**: 没有明确时间、采用参考模式时，用户 MUST 能自行选择日间、早班、晚班中的一种或多种。系统只执行已选类型；不因日间已可行而取消已选早晚检查，不为复用结果额外执行未选类型。各类型内部保持逐点尝试、命中即停和相同时点复用。
- **FR-014**: 默认初筛中，只要存在已选参考在某个检查日期的去回均符合上限，即可给“可以通勤，可以尝试投递”的主结论，附带适用日期/时段及其他已查不符合方向。全部已选范围都确定无合格去回时才给范围内负向结论；无正向证据且仍有无法判断项时保持待确认。明确岗位的必需班次仍按全部必需安排判断，不用一个参考成功替代已知岗位要求。
- **FR-015**: 整周检查过程中 MUST 显示进度并允许取消；修改影响判断的输入后旧检查结果不得覆盖当前输入。后台仅为当前请求短期暂存结果，不提供历史记录，过期后可重新发起。
- **FR-016**: 已给明确上下班时间但星期未明确时，七天仅为可用日期检查范围，不代表七天都必须上班。有可行日期可给带范围的正向参考；星期已明确的必需安排仍须全部满足。取消某些轮班选项不改变原排班周期长度。

### Key Entities

- **初筛条件**：出发地、工作区域、单程上限、明确班次或个人时间（可选）、用户选择的参考类型、七天范围。
- **候选时间点**：具体日期、到岗或离岗时刻、去程/回程、优先顺序、参考类别。
- **方向结果**：命中时间、最优合格路线、超限/无路线/未知原因；同一时点可被多个参考复用。
- **时段参考**：去程窗口和回程窗口的交通覆盖证据，不构造固定工作时长，不等同于雇主真实班次。
- **主要结论**：可行/不符合/待确认、方向原因、适用日期和时段、参考性质。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 未填写 availability 和精确门店的用户，仅凭两个完整 postcode 和默认上限即可发起初筛。
- **SC-002**: 所有参考分支首个合格时间点之后均不发生额外试探；边界用例无重复的相同时点查询。
- **SC-003**: 跨午夜、重复06:30、早班提前停止未覆盖06:30、不施加工时限制、提供方失败五类用例均有明确且不误判的结果。
- **SC-004**: 每次初筛首屏只有一个主要结论；负向结论说明受影响方向及检查范围，未知用例不显示为不可通勤。
- **SC-005**: 首日早班使用首日上午；次日早班复用前一日晚班已完成的同日期上午参考，重复检查次数为零；末日晚班仍使用必要的第八天节点。早班日期偏移为零、晚班日期偏移为一天，不把同钟点不同日期当作同一结果。
- **SC-006**: 未选参考类型的额外检查次数为零；所选类型全部得到检查，日间命中不导致所选早晚被跳过；“日间可行、早班去程不符合”的验收用例给正向主结论并保留方向原因。

## Assumptions

- 用户已授权执行；实现和测试完成情况以tasks.md、CHANGELOG.md为准。
- 用户给定的时间顺序和按需停止作为本稿基础；“找到结果”按现有单程上限和目标时刻判定，而非只看是否返回路线。
- **用户确认：只做时段初筛**。四小时是选择参考回程时点的解释，不是产品限制。上午已找到符合上限的回程，即作为该参考窗口有交通的依据，后续时点不再逐一查询；不因为06:30去程目标与已命中的上午回程之间不足四小时而增加查询或判待确认。不把未经查询的具体时刻显示为实测路线、时长或确定班表。
- **用户确认：汇总结论**。无明确排班时，至少有一个日期的已选参考去回窗口可行，即给带适用范围的正向申请参考；日间可行而早班不行时仍显示可以通勤，并说明早班不符合方向。部分日期可行不代表全周可行，未知不作为确定失败。岗位日期/班次已明确时仍覆盖全部必需安排。
- **用户确认：选择检查范围**。由用户选择日间、早班、晚班，不由系统在日间命中后自动跳过其他已选类型。具体执行先后由实现确定，单组候选按既定顺序执行。
- **实现默认**：初始勾选日间，减少首次录入；用户可自由改选或多选。该默认是本轮实施选择，不称作用户此前指定的规则。
- 不再保留最少工时或自动跳过已选早晚的建议；未额外采用按行业模板或付费服务。
